## 📌 TL;DR（执行摘要）

- **核心目标**：从 Databuff 提炼可借鉴功能，补强基石已知短板——AI 入口未前置（仅 ⌘K + 1 个埋藏 Tab）、告警阈值偏静态、巡检智能化不足。
- **关键决策**：高优三项（**智能问数/AI 入口前置、自适应告警+突变检测、巡检自发现**）直接并入 **M3 集成与智能**；**MCP 开放接口**单列为净新增里程碑 **M6 开放生态**；基础设施语义不同的项（Trace / QPS / JVM / 服务调用拓扑）**勿照搬**。

## 1. 竞品全景图（来自竞析）

Databuff 定位 **"AI 原生 OpenTelemetry APM"**——标准遥测数据底座（看清 Trace/指标/拓扑/告警）+ AI 智能大脑（直接读遥测数据，用对话完成查询/巡检/诊断）原生融合。

- **基础可观测**：故障排查（服务红绿灯）、链路追踪 Trace、服务指标（QPS/延迟/错误率/JVM）、服务拓扑（自动绘制）、告警（灵活阈值+突变检测+定时评估+事件回看）、极简 3 组件部署。
- **AI 原生**：智能问数（NL 查指标/Trace/拓扑/告警）、服务巡检（无预设阈值自动发现异常）、故障分析（综合多源给诊断结论）、MCP 开放、多智能体协同（AI 大脑 + 数字专家：问数/巡检/分析）。
- **未做**：智能降噪、故障预测（当前侧重异常发现与故障后诊断）。
- **适用场景**：快速落地 APM 不想维护重型平台；让研发/运维用对话代替查图表；开源可私有化 AI 运维；技术选型评估。

> ⚠️ **层级边界（关键）**：Databuff 属**应用层 APM**（服务/Trace/QPS/JVM）；基石属**基础设施层 AIOps**（设备/电路/日志/容量）。借鉴时"范式可迁移"，但"数据对象不可套"。

## 2. 功能对比矩阵

| 维度 | 我方 基石（基础设施层） | Databuff（应用层 APM） | 借鉴判断 |
|------|------|------|------|
| 数据对象 | 设备/电路/日志/容量/告警 | 服务/Trace/QPS/JVM | 对象不同，范式可学 |
| AI 原生架构 | 有可插拔 LLM 后端，但入口埋藏 | AI 原生，非外挂聊天框 | **学架构，勿学"外挂 Tab"** |
| 自然语言问数 | 缺失 | NL 查指标/Trace/拓扑/告警 | **高优借鉴**（限基础设施对象） |
| 自适应告警 | 阈值偏静态 | 灵活阈值+突变检测+事件回看 | **高优借鉴** |
| 巡检 | 模块存在，智能化待提升 | 无阈值自动发现异常 | **高优借鉴** |
| 根因/RCA | 跨模块能力弱 | 多源综合给结论 | 中，需先清数据层（M4） |
| 拓扑 | circuits 模块 | 服务调用自动绘制 | 中，改"电路/设备依赖"语义 |
| 红绿灯视图 | 缺失 | 一眼锁定异常实体 | 中，改 infra 实体 |
| MCP 开放 | 缺失 | 外部 Agent 可调能力 | 中，生态扩展（M6） |
| 多智能体协同 | 缺失 | AI 大脑+数字专家并行 | 中，复用过剩 AI 后端 |
| 极简部署 | 较重（前后端+PG+Redis） | 3 组件一条命令 | 低，企业需合规高可用 |

## 3. 市场趋势与用户感知

- **趋势**：AIOps 正从"图表堆叠"走向"对话即运维 / AI 原生"，自然语言查询与自适应检测成为标配预期；OpenTelemetry 成标准遥测底座。
- **用户感知（Databuff 文档）**：研发/运维希望"用对话代替查图表"降低使用门槛。映射到基石，目标用户是**基础设施运维/网络/容量管理员**，同样存在"看板多、定位慢"的痛点，对话式入口价值成立。

**依赖与升级安全风险**
- #1/#2/#3/#4/#6：依赖 M3 LLM 四场景 + IdP；外部 LLM 集成；可灰度；无 schema 变更；须配套权限/审计满足升级安全。
- #5 MCP：依赖 M3 IdP 鉴权 + API 网关；**净新增对外暴露面，须前置安全评估与鉴权绑定**；可灰度；需工具注册机制。
- #7/#8：并入 M4，复用现有 alembic 与灰度机制，零净增量风险；#8 的 OTel 是 M4 数据层双源清理的自然延伸，**#8 的 schema 变更须走 alembic 迁移**。

## 6. 范围护栏（来自路径补充，已与竞析对齐）

**层级边界护栏**
- 自然语言问数：查询对象限为**指标/电路/设备/告警**，**不照搬 Trace/QPS/JVM**。
- 红绿灯/拓扑：语义改为"**电路/设备依赖关系**"，非应用服务依赖图。
- 根因定位：多源数据仅取 **alerts+logs+circuits**，不引入应用层 APM 信号。

**防重复建设护栏**
- M4 已有"静默异常清理"（≈降噪）。巡检免阈值、根因定位**仅做"自发现+诊断"，明确不扩展为"故障预测"**，与 M4 降噪分工，避免重复造轮子。
- OTel 是 M4 数据层双源清理的延伸，**不新建独立遥测采集体系**。

## 7. SWOT 与差异化机会

- **S（优势）**：已有可插拔 LLM 后端，AI 能力"过剩"；基础设施数据（设备/电路/日志）齐全，是应用层 APM 不具备的护城河。
- **W（劣势）**：AI 入口埋藏、告警静态、巡检智能化不足、测试覆盖率极低。
- **O（机会）**：对话式入口 + 自适应检测是行业标配预期，快速补齐即可显著提效。
- **T（威胁）**：若只做"外挂聊天框"式 AI，将重复 Databuff 明确否定的反模式，价值打折。
- **差异化**：基石应聚焦**基础设施语义的对话式运维**（电路/设备/容量），而非追随应用层 APM 的 Trace 叙事。

## ⚠️ 待确认 / 假设 / Non-goals

- **待确认**：M3 的 LLM 四场景具体范围需与现有可插拔 LLM 后端对齐；MCP（M6）是否本期启动取决于生态诉求强度。
- **假设**：基石当前 AI 后端确为"能力过剩、仅入口埋藏"（来自前期审计结论）；Databuff 文档未开放更细功能细节，部分判断基于产品介绍页。
- **Non-goals（本期不做什么）**：
  - 不照搬 Trace 追踪、QPS/JVM 等应用层 APM 指标。
  - 不照搬"服务调用拓扑"语义（改为 infra 依赖）。
  - 不建设"故障预测"能力（与 M4 降噪分工，Databuff 亦未做）。
  - 不做"外挂聊天框"式 AI（须前置融入工作流）。
  - 不追求 3 组件极简部署（企业需合规高可用）。
